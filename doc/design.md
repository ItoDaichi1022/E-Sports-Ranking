# トーナメント運営＆ランキングサイト 設計ドキュメント

---

## 1. 目的

- 自作サイト内で **トーナメントの運営**（募集・ブラケット生成・勝敗入力）と **個人ランキング** を完結させる
- 選手が**自分のアカウント**を持ち、自分のプロフィールを自分で編集できる
- 無料・低メンテナンスで運用する

## 2. 想定規模

- 1大会あたり 25〜60人程度
- 1シーズンで数百試合程度
- 集計（ランキング・戦績）はブラウザ内で行う。サーバー側の計算処理は持たない

ただし**大会と試合は開催のたびに増え続ける**ので、起動時に全部読む作りにはしない。
増えるデータ（エントリー・試合結果・お知らせ・対戦表）は、それが必要な画面を
開いたときに必要な分だけ取りに行く（`js/db.js` の `ensure〜` 系）。

| データ | 読むタイミング |
|---|---|
| 選手・大会・公開ランキング | 起動時（大会は一覧に出す人数だけDB側で数えてもらう） |
| 優勝の記録 | 起動時（一覧の「優勝: ○○」用。1大会1〜2行） |
| お知らせ | 起動時は最新数件。全件はお知らせ一覧を開いたとき |
| エントリー・チーム | その大会の詳細・対戦表を開いたとき |
| 試合結果 | その大会の対戦表を開いたとき／選手ページはその選手の分だけ |
| 対戦表(JSONB) | その大会の対戦表を開いたとき |
| 全件 | 運営がランキングを集計するとき・募集を締め切るとき（`ensureFullData`） |

この方針のため、`state.tournaments[].entrantIds / participantIds / teams` は
**詳細を読み込んだ大会でしか埋まらない**。一覧で人数を出すときは
`entrantCount` / `participantCount` を使う（`js/state.js` の説明を参照）。

## 3. 技術構成

| 役割 | 使うもの | 備考 |
|------|----------|------|
| ホスティング | Cloudflare Pages | 無料・帯域無制限。ビルド工程なし。URLにアカウント名が出ない |
| データベース | Supabase (PostgreSQL) | 無料枠500MB |
| 認証 | Supabase Auth | Google / Discord（OAuthのみ） |
| アクセス制御 | 行レベルセキュリティ (RLS) | 閲覧は全員、書き込みは本人と運営に限定 |
| 自動更新 | Supabase Realtime | 変更が全端末へプッシュされる |
| ランキング計算 | ブラウザ内 JavaScript | サーバー計算不要 |

- **ビルド工程を持たない**方針は維持している。supabase-js は `js/vendor/supabase.js` に同梱し、
  CDNの障害でサイトが止まらないようにしている。
  唯一の例外がキャラクター画像の変換（`scripts/build-characters.mjs`、`sharp` を使う）だが、
  これは**素材を差し替えたときだけ手で流すもの**で、デプロイの手順には入らない。
  出力（`img/characters/` と `js/characterData.js`）はリポジトリに入っているので、
  デプロイは今までどおり「そのまま上げるだけ」で済む。
- **リポジトリに入れる画像はWebP**（`img/` 以下、ロゴもキャラクターもアイコンも）。
  唯一の例外は `img/icon.png` で、iOSのホーム画面のアイコン（`apple-touch-icon`）だけが
  WebPを読まないため、同じ絵をPNGでも置いている。置き場と作り方は
  [`img/README.md`](../img/README.md)。
- セットアップ手順は [`supabase/SETUP.md`](../supabase/SETUP.md)、スキーマは [`supabase/schema.sql`](../supabase/schema.sql)。

### 以前の構成からの移行

当初はGitHubリポジトリ内のJSONファイルをデータベース代わりに使い、共有の書き込みトークンで
認証していた。ユーザーアカウント・本人だけが編集できる制御・エントリーの同時登録は
この方式では安全に実現できないため、Supabaseへ移行した。

移行によって不要になったもの：

- 楽観ロックとレコード単位の三方マージ（約250行）。Postgresは行単位で書き込むため、
  別々の大会・別々の選手を同時に編集しても競合しない
- コミットSHAを比較する10秒ポーリング。Realtimeの購読に置き換えた
- 変更をまとめてコミットする自動保存デバウンス。各操作がその場で書き込まれる

## 4. 権限モデル

| | 閲覧 | 自分のプロフィール編集 | エントリー | 大会を作る | その大会の運営 | 全大会の運営 | ランキングの集計 |
|---|:---:|:---:|:---:|:---:|:---:|:---:|:---:|
| ゲスト（未ログイン） | ○ | – | – | – | – | – | – |
| 選手（`role = 'player'`） | ○ | ○ | ○ | ○ | ○（自分の大会） | – | – |
| 運営（`role = 'admin'`） | ○ | ○（全選手） | ○ | ○ | ○ | ○ | – |
| 持ち主（`role = 'owner'`） | ○ | ○（全選手） | ○ | ○ | ○ | ○ | ○ |

**大会は誰でも作れる**。運営権限を配って回るのではなく、大会ごとに運営を持たせる形にした
（`tournament_organizers`）。作った人はDBのトリガで必ずその大会の運営に入り、
当日いっしょに進行する人は大会作成・編集の画面から名前で指名する。
指名された人に開くのはその大会だけで、他の大会には何もできない。

判定に使う関数は3つ。役割が違うので混ぜないこと。

| 関数（DB） | 対応するJS（`js/auth.js`） | 何を聞いているか |
|---|---|---|
| `is_owner()` | `isOwner()` | サイトの持ち主か。ランキングの集計・保存と `#reveal` だけ |
| `is_admin()` | `isAdmin()` | サイト全体の運営か（owner を含む）。お知らせ・選手の削除/統合・権限の付け外し |
| `is_tournament_admin(id)` | `canManageTournament(id)` | **この大会**の運営か。大会にぶら下がる操作はすべてこれ |

大会にぶら下がるもの（`tournaments` の更新・削除、`brackets`、`matches`、
`tournament_entries`、`tournament_teams`、`tournament_rounds`、対戦チャットの削除、
運営への報告の閲覧・対応）は、例外なく `is_tournament_admin(tournament_id)` で判定する。
ここに `is_admin()` を書くと「全大会を触れる人か」を聞くことになり、
大会ごとの運営という考え方が崩れる。

- **閲覧は認証不要**。大会履歴もブラケットも選手プロフィールもログインせずに見られる。
  唯一の例外が**準備中（`draft`）の大会**で、これはその大会の運営にしか返さない。
  ぶら下がるもの（エントリー・チーム・運営・対戦表・回戦・試合結果）の閲覧ポリシーも
  例外なく `is_tournament_visible()` を通す ── 本体だけ隠しても、チーム名や組み合わせが
  読めるなら隠したことにならない。
  作った本人（`created_by`）を判定に混ぜてあるのは、`insert ... returning` で返る行にも
  SELECTポリシーが掛かる一方、作成者を運営に入れるのは `after insert` のトリガで、
  その時点ではまだ `tournament_organizers` に行が無いため。
- 制御はすべてデータベース側のRLSで行う。画面上のボタンの出し分けは利便性のためのもので、
  防御ではない（APIを直接叩かれても通らない）。
- 一般ユーザーが自分を運営に昇格させられないよう、`role` と `user_id` は
  **列単位のGRANTでUPDATE不可**にしてある。変更は `admin_set_player_role` などのRPC経由でのみ可能。
  `owner` が絡む変更だけは owner にしか許さない（運営が自分を持ち主に格上げしたり、
  持ち主の権限を降ろしたりできないようにする）。
- 大会画像（Storageの `images` バケット）へのアップロードは、選手登録さえ済んでいれば通す。
  大会を誰でも作れる以上、画像を付けられないと大会が作れないため。差し替え・削除は
  `is_admin()` のままにしてある ── 開けると他人が上げた画像を消せることになり、
  使われない画像が残る（容量だけの害）より、間違って消える事故のほうが取り返しがつかない。
- アイコン画像はStorageの `avatars` バケットに置く。閲覧は誰でも可、書き込みは
  `avatars/{自分のuser_id}/...` に限る（先頭フォルダ名を `auth.uid()` と突き合わせる）ので、
  他人のアイコンは差し替えられない。
- RLSで弾かれたUPDATEは、エラーではなく**0行更新の「成功」**として返る。そのまま
  「保存しました」と表示すると原因の分からない不具合になるため、`js/db.js` の
  `savePlayer` は `.select()` で実際に更新された行を確認している。
- RLSポリシーの中から `players` を参照すると無限再帰になるため、
  管理者判定は `security definer` 関数 `is_admin()` に切り出している。
  `is_tournament_admin()` も同じ理由で `security definer` にしてある
  （`tournament_organizers` の読み取りポリシーに引っかからないようにするため）。

## 5. 選手の識別設計

- **選手 ＝ ユーザーアカウント**。`players.user_id` が `auth.users` を指す。
  新規の選手は自分で登録し、その瞬間から自分のプロフィールを編集できる（運営の承認は不要）。
- `user_id` が null の行は**運営が代理登録した選手**。旧データから移行してきた選手や、
  アカウントを持たない参加者がこれにあたる。本人がログインしてきたら、
  運営が選手一覧から `admin_merge_players` で対応付ける（初回だけの作業）。
- **不変の一意キーは `players.id`（uuid）**。試合結果もランキングもこのIDに紐づく。
- **表示名は可変**。変更すると旧名が `past_names` に残るので、名前が変わっても戦績が分断されない。
- **ゲームアカウントIDは本人が自由に記入・変更できる表示用の欄**。以前は主キーだったが、
  編集可能にするにあたり主キーから外した（移行時に旧IDは `game_account_id` へ引き継いでいる）。

### 使用キャラクター

`players.main_characters`（`text[]`）に、選手が使うキャラクターを**選んだ順**で持つ。
**先頭がメインキャラクター**で、画面に出るのはこの1人だけ ── プロフィールのヒーロー
（`js/app.js` の `playerHeroHtml`）と、ランキング・選手検索の行
（`js/characters.js` の `characterRowArtHtml`）。順番そのものが情報なので、
入力欄では「メインにする」で並べ替えられる。

入っているのは `キャラID:スキンID` の形の文字列（例: `sivi:wolf-spirit`、
`sophia:kendo-bk`）。この2つを合わせると画像1枚が決まる。

```
img/characters/sivi/wolf-spirit.webp      角240px（選ぶ画面の一覧用）
img/characters/sivi/wolf-spirit@lg.webp   長辺480px（大きく見せる用）
```

- **スキンまで持つ**のは、同じキャラクターでも見た目が大きく変わるため。
  キャラクター単位で丸めると、選手が「自分はこれ」と示したものが表せない
- **列は増やしていない**。`text[]` の中身の書き方を決めただけなので、
  スキーマの変更もマイグレーションも要らない
- **この仕組みより前に文字で入力された値**（「シビ」など）はそのまま残る。
  読めない文字列は「絵の無いキャラクター」として文字だけ出す
  （`js/characters.js` の `parseCharacterRef` が `known: false` を返す）。
  選ぶ画面には持ち込めないので、閉じたあと末尾に戻す ── 絵を選び直しただけの
  つもりで前の登録が消えないように。外れるのは札の × を押したときだけ

キャラクターとスキンの一覧（`js/characterData.js`）は**配布素材から自動生成**する。
元素材は2.3GBあり、配信もGitもせず、作業機にも普段は置かない（作り直すときだけ
取り直す）。生成物はリポジトリに入っているので素材が無くてもサイトは動く。
詳しくは [`img/README.md`](../img/README.md)。

画面での使い方は2つに限っている。

| | 場所 | 見せ方 |
|---|---|---|
| 立たせる | プロフィールのヒーロー（次章） | 右側に全身。背景として 0.55 で透かす |
| 敷く | ランキング・選手検索の行 | 名前の後ろに滲ませる（0.2〜0.3） |

**敷くときは必ず透かす。** このサイトは黒＋アシッドグリーンの2色で通していて、
キャラクターの絵はそこに初めて入る「色の塊」になる。表の行のように文字の後ろへ
回すときは、そのまま置くと画面の主役を奪い、操作できる場所を示す緑より前に出てしまう。
プロフィールのヒーローも背景なので透かすが、そちらは文字とほとんど重ならない配置なので
0.55 まで戻してある（次章）。

**縦横比はばらつく。** 切り抜きの高さ÷幅は 0.75〜2.73（226枚の実測）。
どこで使うにせよ、画像の実寸を当てにした大きさの決め方をしないこと
（次章「大きさを画像の実寸から切り離す」）。

## 5.5 プロフィールの構成

選手ページとマイページは同じ部品で組む（`js/app.js` の `playerHeroHtml` ほか）。
マイページは「他の人からどう見えるか」の確認場所なので、見た目が違うと確認にならない。

### 絵は背景。ただし全身を見せる

もともとキャラクターは**本文の真後ろ**に敷いてあり、戦歴カードもランクも
その上に重なっていた。同じ面積を「絵を見せる」役と「数字を読ませる」役で取り合う形で、
顔と上半身は箱の裏に隠れ、絵が透けるぶん数字も読みにくかった。

いまは**場所を分けたうえで背景に置く**。

- **上段は名前が横いっぱい、中段を左右に割る**（左＝ランク、右＝キャラクター）。
  名前だけ半分に縛らないのは、一番格上で、しかも1行と決めているから ──
  幅を削るとすぐ `…` になる
- **絵が名前にかぶらないのは「段が違う」から。** 座標で避けているのではないので、
  過去名の有無で名前の高さが変わっても関係は崩れない
- 列は `minmax(0, 1fr)` で割る。素の `1fr` は中身より狭くならないため、
  折り返さないランク表記が入ると左の列が押し広がり、半々でなくなる
- **左右の境目に線は引かない。** 境界線も、地色の切り替わりも置かない。線を引くと
  「2つの箱を並べた」ように見えて、絵が背景であることが伝わらなくなる
  （下段との境目は別。あちらは文字と文字の境なので線を引く ── 後述）
- 重なったときのために、絵は文字より**後ろ**（`z-index: 0`）。名前は必ず読める
- **切り取らない。** 全身がカードに収まる大きさにする。頭や足が切れていると、
  背景として流し見たときに「見切れた画像」の違和感だけが残る
- 絵の面に地色は敷かない。足元の淡い光だけ ── 面を敷くと、絵ではなく四角い板が
  背景に浮いてしまう

透かす濃さは 0.55。以前 0.16 まで落としていたが、それでは選んだキャラクターが何なのか
分からず、選ばせた意味が無かった。文字とほとんど重ならない配置なので、
判別できる濃さまで戻してある。

**絵を大きくしたいときは `.player-hero-art` の `height`（島の幅の 44.32%）を上げる。**
全身を収める決まりなので、中段の高さがそのまま絵の背丈の上限になる。

**その高さを絵の升が持っているのは、絵に中身としての背丈が無いため。**
絵は `position: absolute` なので、升に高さを与えないと段ごと潰れる。割合で持たせて
あるので、島が広がれば絵も同じ割合で大きくなり、自己紹介が何行あっても縮まない
（自己紹介は島の外にあり、島の段の取り合いに加わらない）。

### 大きさを画像の実寸から切り離す

**スマートフォンで、再読み込みのたびに絵の大きさが変わる**という不具合があった。
原因は `max-width`/`max-height` と `width: auto` の組み合わせで、
**実寸が分かって初めて大きさが決まる**書き方をしていたこと。読み込みの前後で
レイアウトが動いていた。

いまは絵を `position: absolute` で流れから外し、幅も高さも
**カードに対する割合だけ**で決める（`width: 100%` / `height: calc(100% - 余白*2)`）。
実寸を参照しないので、読み込みが済んでいようがいまいが、どの切り抜きだろうが、
位置と大きさは一定になる。

- **`width`/`height` を `auto` にしないこと。** `img` は置換要素なので、`auto` は
  「`left`/`right` いっぱいに広げる」ではなく「実寸のまま」を意味する。
  `left`/`right`/`top`/`bottom` を全部指定しても広がらず、実寸のまま飛び出す
- 縦横比は `object-fit: contain` が保つ。縦長でも横長でも全身が箱に収まる

### 左半分の文字は折り返さない

**選手名・順位・その但し書き**（「ランキング対象外」など）は、いずれも
`white-space: nowrap` で1行に保つ。

日本語は単語の区切りが無く、既定では文字と文字の間でいくらでも改行できるので、
狭い左半分に置くと「ランキング対」「象外」のように語の途中で割れる。
また名前が2行になると下のランクの位置が動き、**フォント（Oxanium）の読み込みが
済む前と後でカードの高さまで変わる**。

- 名前は上段で横いっぱいを使えるので、ふつうの長さなら切れない。
  それでも収まらなければ末尾を `…` にし、全体は `title` 属性から読める
- 順位と但し書きは**あふれさせる**。左半分は狭く、「ランキング対象外」は入りきらない。
  はみ出した先にあるのは背景の絵だけなので、切るより読めるほうを取る

### 読む順を決める。ただし「その人自身」は1つの島にまとめる

上から順に格が下がるよう並べる。ただし段の切れ目＝カードの切れ目ではない。

| | 段 | 中身 | 置き場所 |
|---|---|---|---|
| 1 | 名前 | 選手名・過去名・アイコン | **島の中**（上段） |
| 2 | ランク／キャラ | 順位・スコア・メインキャラクター | **島の中**（中段。左右に割る） |
| 3 | 自己紹介・直近の戦績 | 紹介文と最新3件の札 | **島の中**（下段。横いっぱい） |
| 4 | すべての戦歴 | 全件の表。`<details>` で畳んである | 島の外 |
| 5 | 連絡先 | ゲームID・SNS | 島の外。区切り線を引いて離す |

- **1〜3段は同じ島（`.player-hero`）に収める。** どれも「この人が何者か」の話なので、
  別のカードに分けると、あいだの隙間のぶんだけ別の話に見える
- **島の中の釣り合いは、幅がいくつでも変わらない。** 基準は iPhone 13 mini の縦
  （375px − 本文の左右余白 ＝ 343px）で見たときの並び。余白も文字も絵の升も、
  島の幅に対する割合（`cqw`）で持たせてあるので、島は大きさが変わっても
  「拡大・縮小しただけ」になる。数値はどれも**13 mini での実寸 ÷ 3.43**で、
  直すときも同じ手順を踏むこと（`rem` のまま足すと、その値だけが取り残される）。
  以前は器（`main`）の 1080px まで幅だけが伸び、中身の大きさは据え置きだったので、
  広い画面ほど間延びして見えていた
- **`cqw` は島の中の要素にだけ書ける。** 単位が指すのは「いちばん近い“先祖”の
  コンテナ」なので、コンテナ自身（`.player-hero-core`）の指定に書くと自分の幅ではなく
  画面幅を見に行く。中段の高さを `grid-template-rows` に書いて画面幅について
  伸びてしまったことがある ── 高さは絵の升（`.player-hero-art`）に持たせている
- **広い画面（721px〜）では、島の横に自己紹介と直近の戦績を置く。** 縦に積んだままだと、
  島を大きくするほど下の文章が画面の外へ遠のく。横に並べれば島は器の半分まで育ち、
  それでも文章は同じ高さから読み始められる。区切りの線も上辺から左辺へ移す。
  狭い画面では縦に積み、島は 343px で頭打ち（切り替わる 721px での島は 336px なので、
  前後で大きさはほとんど変わらない）
- **自己紹介・戦績の側は実寸（`rem`）のまま。** 読ませる文章と一覧なので、
  置き場所が変わっても文字の大きさは変えない。割合で拡大するのは島だけ
- 全件の表と連絡先は島の外なので、これまでどおり器の幅いっぱいに広がる
- **下段との境目には線を引く。** 左右の境目に線を引かないのとは事情が違う ──
  あちらは線があると絵が板に見えるが、下段は文字と文字の境なので、
  線があるほうが段の変わり目が分かる。線は左右を少し引っ込める
  （端まで届かせるとカードを2枚に割ったように見える）
- **全件の表だけは島の外。** 開くと何十行にもなるので、島の中で伸ばすと
  名前とランクが画面の外へ流れていく
- **直近の戦績を表より先に置く**のは、プロフィールを開いた人が「いま何位か」の次に
  知りたいのが「最近どこまで勝ったか」だから。表は全件を等しく並べるので、
  一番新しい1件を探すのに目が要る
- **熱量は大きさの対比で出す**。ランクは数字を大きく、単位と補足を小さく落とす。
  塗りや発光で作らないので、可読性を削らずに済む
- 自己紹介も戦績も無い人には、下段ごと出さない（`:has()` で中身の有無を見る）。
  線と余白だけが残ると、何かが抜け落ちたように見える

**下段の列は `minmax(0, 1fr)` で明示する。** 省略して暗黙の `auto` 列にすると、
長い自己紹介が折り返さず `max-content` まで横に伸びる（1035px の枠に対して
5259px まで伸びるのを実測した）。日本語は単語の区切りが無いので、
一度伸びると一行のまま流れていく。

## 6. データベース設計

テーブル定義の実体は [`supabase/schema.sql`](../supabase/schema.sql)。要点だけ記す。

| テーブル | 役割 |
|---|---|
| `players` | 選手＝アカウント。プロフィール（アイコン・自己紹介・使用キャラ・SNS・ゲームID）と `role` を持つ。`main_characters` の中身の形は前章「使用キャラクター」 |
| `tournaments` | 大会。`status` でライフサイクルを表す。`capacity` は定員、`entry_deadline` はエントリー締切（掲示だけで、自動では締め切らない） |
| `tournament_organizers` | その大会を管理できる選手。作った人はトリガで必ず入る（前章「権限モデル」） |
| `tournament_teams` | チーム戦（2v2）でブラケットの枠に入るチーム。`seed` と `placement` を持つ |
| `tournament_entries` | エントリー。締切後に `seed` が入る。主キーは (大会, 選手)。チーム戦では `team_id` が入る |
| `brackets` | ブラケット1件をJSONBで保持 |
| `tournament_rounds` | 回戦ごとの開始と配信台。開始するまで選手は結果を入力できない |
| `matches` | 確定した試合。ランキング計算の唯一の入力 |
| `match_chat_messages` | 対戦カードごとのチャット。当事者と運営だけが読み書きできる |
| `match_chat_reports` | チャットからの運営への報告。未対応のものがある大会に印を出す |
| `published_rankings` | 集計を「前回の順位」として保存した瞬間のスナップショット（書けるのは持ち主だけ） |

- **ブラケットだけはJSONB**にしている。`js/bracket.js` が扱うオブジェクト構造をそのまま保存でき、
  ブラケットの生成・進行ロジックを一切書き換えずに移行できたため。
  ブラケットは常に1大会分をまとめて読み書きするので、正規化する利点も薄い。
- **常時計算するランキングスコアはどこにも保存しない**。順位発表の画面では常に `matches` から再計算する。
  例外として、そこで「前回の順位として保存する」を押した瞬間だけ、`published_rankings` に
  1行追加する（上書きではないので、いつ何を保存したかの履歴が残る）。
  サイトにランキングの一覧は無い ── 順位はお知らせや動画で発表する。それでも保存の
  仕組みが要るのは、順位変動（▲▼―NEW）と選手ページのランク表示が「前回の順位」を
  必要とするため。
- 集計ロジックを変えても過去データから作り直せて、データ不整合が起きない。

### 出場の単位（entrant）

ブラケットの枠に入るのは、個人戦（1v1・リレー）では選手、チーム戦（2v2）ではチーム。
この2つを **出場枠（entrant）** としてまとめて扱う。

| | 1v1・リレー | 2v2 |
|---|---|---|
| `entrantIds`（出場枠） | 選手ID | チームID |
| `participantIds`（出場した人） | 選手ID | メンバー全員の選手ID |

- **枠数・シード・定員・大会規模Tier は `entrantIds` で数える**。16チーム32人の大会は
  「定員16チーム」であって32人ではない。DBの定員トリガーも
  `count(distinct coalesce(team_id, player_id))` で同じ区切り方をするので、
  画面に出る枠数と定員判定が必ず一致する。
- **選手ページ・選手削除の判定は `participantIds`**。チーム戦でも両メンバーが
  「この大会に出た」と記録される。
- 個人戦ではこの2つは同じ配列になるため、既存の大会の挙動は一切変わらない。

チームIDもuuidなので、**`brackets` のJSON構造は変えていない**（`player1Id` / `player2Id` の
まま）。入っているIDが選手かチームかは大会の `match_type` で決まり、名前の解決だけが
`js/bracketView.js` で分岐する。保存済みのブラケットを一切書き換えずに済んだ。

そのため、対戦方法を **チーム戦と個人戦の間で切り替えることは禁止**している
（`js/bracket.js` の `updateTournament`）。既にエントリーがある状態で切り替えると、
保存済みの枠の意味が変わって対戦表と成績が壊れるため。

### in-memory state との対応

`js/db.js` がデータベースとアプリの唯一の境界で、snake_case ⇄ camelCase の変換もここだけで行う。
そのため `js/ranking.js`・`js/bracket.js`・`js/playerStats.js` などの計算・描画ロジックは
ストレージを一切意識しない（`js/state.js` の形だけを見て動く）。

`tournaments.entrantIds` は `tournament_entries` を `team_id ?? player_id` でまとめ、
シード順（未確定なら登録順）に並べたものとして組み立てられる。ブラケットのシード番号表示も
この並びを使う。個人戦のシードは `tournament_entries.seed`、チームのシードは
`tournament_teams.seed` にある。

### チーム戦の試合の記録

`matches` は個人戦なら `winner_id` / `loser_id`、チーム戦なら `winner_team_id` /
`loser_team_id` が入り、制約でどちらか一方だけを許す。別テーブルに分けると
「1大会の試合は `matches` を見れば分かる」性質が崩れ、`js/db.js` の
`syncTournamentProgress` の照合が二重になるため、同じテーブルに置いている。

この形の副産物として、**チーム戦の勝敗は個人の通算成績（W-L）に混ざらない**。
`js/playerStats.js` は「自分が勝者か敗者か」で試合を絞るが、チーム戦の行は選手列が
空なので引っかからないため、特別な除外処理を書かなくても成立する。個人ランキングが
2v2を対象外にしているのと揃った扱いになる。

最終順位（`placement`）はチーム行に書いたうえで、**同じ値をメンバー全員のエントリー行にも
書き写す**。二重に持つことになるが、こうしておくと選手ページ・ランキングカードが
チームの存在を一切知らずに「優勝」「ベスト4」を出せる。

### published_rankings のスナップショット形式

集計期間は運営がカレンダーで選んだ開始日・終了日（`period_start` / `period_end`）。
どちらも省略でき、省略した側は無制限になる（両方省略なら全期間）。
`period_months`（「直近Nか月」形式）は移行前の古いデータにだけ残り、新規の公開では書き込まない。

```json
{
  "published_at": "2026-07-19T12:34:56.000Z",
  "period_start": "2026-04-01",
  "period_end": "2026-06-30",
  "data": {
    "rankings": [
      { "id": "uuid", "name": "Gyu", "score": 100, "tournamentsPlayed": 4,
        "rank": 1, "previousRank": 2,
        "bestAchievement": { "label": "優勝", "tournamentName": "○○杯",
                             "participantCount": 32, "tier": "Tier 4", "value": 32 } }
    ]
  }
}
```

- `previousRank`：公開した瞬間の「ひとつ前に公開されていたランキング」での順位。
  前回に存在しなかった選手は `null`（NEW扱い）。公開時に一度だけ計算して焼き込むため、
  以後 `matches` が変わっても遡って変化しない。
- `bestAchievement`：集計期間内の出場大会から、参加人数÷勝ち上がり深さ（優勝=1、準優勝=2、
  ベストN=N）が最大の成績を1つ選出したもの。**現在これを表示する画面は無い。**
  発表カード画像の書き出し機能で使っていたが、その機能は削除した。
  公開済みのスナップショットにはすでに焼き込まれているため、計算と保存は残してある
  （消すと過去の行と形が変わるうえ、選手ページなどで使いたくなったときに作り直しになる）。
- 閲覧者のランキングページ・選手個人ページの「現在ランク」は、常に最新のスナップショットを表示する。

## 7. 大会のライフサイクル

```
draft ──公開──▶ recruiting ──締切──▶ running ──決勝確定──▶ finished
（準備中）        （募集中）           （進行中）          （終了）
   └────────────── 公開（参加者を直接選んだ大会）──────────┘
```

- **draft** — 作った直後は必ずここから始まる（`js/app.js` の作成フォーム）。
  **運営が「公開」を押すまで、選手にもゲストにも一切見えない** ── 画面から隠すだけでなく、
  RLSが行そのものを返さない（`tournaments_select` と `is_tournament_visible`。
  `supabase/migration-022.sql`）。大会一覧にも、共有リンク `/t/{大会ID}` のプレビューにも出ない。
  作った瞬間に世に出ると、打ち間違いも決めかねている日付もそのまま広まり、取り消しがきかない
- **公開** — 大会ページの1つのボタン（`js/entries.js` の `adminControls`）。行き先は大会の作り方で決まる。
  エントリーを募集する大会は `recruiting` へ、運営が参加者を直接選んだ大会は
  （作成時点で対戦表まで出来ているので）`running` へ直接進む。
  募集中から `draft` へ戻すこともでき、その場合は公開が取り下げられて再び運営にだけ見える状態になる
- **recruiting** — 募集ページに掲載される。ログイン済みユーザーは「エントリー」ボタン1つで参加登録でき、
  募集中はいつでも取り消せる。チーム戦（2v2）だけは後述のとおりフォームになる
- **エントリー締切（`entry_deadline`）** — 「いつまでに入ればよいか」を運営が掲げるための時刻。
  募集一覧のカードと、大会詳細のエントリーボタンの隣に、残り時間つきで出る（`js/entries.js` の
  `entryDeadlineElement`）。**時刻が来ても自動では何も起きない** ── 締め切るのは運営の操作のままで、
  過ぎたあともエントリーは受け付ける。集まりが悪ければ延ばす・早く揃えば早めるという判断は現場にあり、
  時刻はその材料として置いている
- **締切時** — エントリー済みの出場枠を**その時点のランキング順に自動整列**してシードを確定し、
  ブラケットを生成する（`js/entries.js` の `seedEntrants`）。ランキングに載っていない選手は
  後ろにまとめ、その中では登録順を保つ。チームのランクは
  **メンバーの中で最も上位のランク**とする
- **running** — 勝敗入力。確定のたびに `matches` へ記録され、各選手のプロフィールの戦歴に即座に反映される。
  運営はその場で確定でき、選手も自分の対戦だけ同じようにその場で確定できる（後述）
- **finished** — 表が全部埋まったあと、**運営が「結果を確定する」を押して初めて**遷移する

### 結果の確定を挟む理由

表の全欄が埋まった瞬間に自動で優勝者を掲げると、入力ミスに気づいて直す前に結果が
広まってしまう。そこで確定という一手間を挟み、それまでは次のものを出さない。

- ブラケット下部の優勝者バナー（`js/bracketView.js` の `showResult` オプション）
- 大会一覧・大会情報の「優勝: ○○」表示（確定前は「結果待ち」）
- 選手ページの大会別成績（確定前は「進行中」。`js/playerStats.js` の `placementLabel`）

確定後に結果を編集し直すと `running` に戻り、再び非公開になる。

### 対戦表の見せ方（全体と回戦ごと）

対戦表は2つの形を持つ（`js/bracketView.js`）。**対戦カードそのものは同じものを使い、
並べ方だけを変えている** ── 見た目が2種類あると、表で覚えた枠が一覧で見つからなくなる。

| 形 | 中身 | 既定 |
|---|---|---|
| `tree` | 左から右へ、勝ち上がりの枝ごと1枚に描く従来の表 | すべての画面 |
| `rounds` | 選んだ回戦の対戦カードだけを縦に積む一覧 | （切り替えで選ぶ） |

**画面の広さで形は組み替えない。** 表を見に来た人がいちばん見たいのは勝ち上がりの枝なので、
狭いというだけで枝を捨てると、見たかったものが画面から消えてしまう。狭さには
**倍率**で応じる ── 地図と同じで、全体を眺めてから気になるところへ寄る
（`js/bracketZoom.js`。下の「対戦表の拡大縮小」）。

ただし**寸法は狭い画面で詰める**（列244px・列間1.5rem・枠の高さ60px。
`LEAF_ROW_HEIGHT_NARROW_PX` と `css/style.css` の640pxのメディアクエリ）。
倍率は「読める大きさ」と「全体を掴む大きさ」を行き来するためのもので、そもそもの寸法が
緩いと、全体を見る倍率がそのぶん小さくなって何も読めなくなる。列の幅（css）と枠の高さ（js）で
持ち主が分かれているので、**境目の値は両方を揃えること** ── 境目をまたいだときだけ
`matchMedia` の `change` で描き直す（`resize` はアドレスバーの出入りでも鳴るので使わない）。

`rounds` は「いまの回戦の対戦カードだけを大きく読みたい」ときのための形として残す。

- 形は右上の切り替えでいつでも変えられる。選んだ形はページを開いているあいだ覚える
  （回戦が進むたびに描き直されるので、そのつど既定へ戻ると選んだ形が勝手に戻ってしまう）
- 開く回戦の既定は**まだ終わっていない最初の回戦**＝いま動いている回戦。
  人が札で選んだあとは、描き直しをまたいでその回戦を保つ
- 進み具合の分母に**不戦勝（BYE）は数えない**。BYEは生成時点で確定済みなので、
  混ぜると「16試合中12試合が確定」のような、何も起きていないのに終わりかけに見える数字になる

### 対戦表の拡大縮小（`js/bracketZoom.js`）

`tree` は枠数に比例して両方向に伸びる。20枠（表の大きさ32）だと 1700×3200px ほどになり、
スマートフォンの画面には到底入らない。そこで**形はそのままに、見る側の倍率を変える**。

3枚重ねで作る。

| 要素 | 役割 |
|---|---|
| `.bracket-stage` | 実際にスクロールする箱。`max-height: 72dvh`（狭い画面は66dvh） |
| `.bracket-sizer` | 倍率をかけた大きさを持つだけの箱。スクロールできる範囲を作る |
| `.bracket` | 対戦表そのもの。`transform: scale` で縮む1枚の板 |

`transform` はレイアウト上の大きさを変えないので、間に `sizer` を挟まないと
「縮めたのにスクロール範囲は元のまま」になる。

- **指1本の送りはブラウザ本来のスクロールに任せる**（`touch-action: pan-x pan-y`）。
  自前で受け止めると、端まで来てもページのスクロールへ続かず、表の中に指が捕まる
- js が受け取るのは**2本指のつまみ**・Ctrl（⌘）＋ホイール・右下のボタン・余白のダブルクリック。
  つまんだ指の間（カーソルの下）にある場所がその場に留まるように、スクロール位置を取り直す
- 引ける下限は「全体が入る倍率」まで必ず届く。寄れる上限は2倍
- 開いた時点で全体が入る倍率が **0.75以上なら全体表示**（8枠までの大会はたいていここ）。
  それより大きな表は等倍で開く ── いきなり読めない大きさで出しても何も分からない
- 倍率と位置は**描き直しをまたいで保つ**。表は Realtime の更新のたびに丸ごと作り直されるので、
  控えておかないと見ている最中に左上へ飛ぶ
- 接続線（SVG）は**倍率をかける前に描く**。座標を `getBoundingClientRect` で測っているため。
  線の太さは `vector-effect: non-scaling-stroke` で保つ（引いたときに骨格が消えては困る）

### 回戦の開始と配信台

選手が勝手に先へ進めてしまわないよう、**運営が回戦を開始するまで結果を入力できない**。

```
運営: 配信台にする試合を選ぶ（任意）──▶ 選手・観戦者にどこが配信に乗るか伝わる
運営: 「R1 を開始」                ──▶ R1 の選手がゲームカウントを入力できるようになる
```

- 配信台は**その回戦で配信に乗せる試合**。基本は1回戦につき1試合だが、全試合を
  配信する大会もあるので複数選べる（`streamed_match_ids` は配列）
- 選ばせ方は一覧ではなく**対戦表の試合そのものを押させる**。どのカードを配信するかは
  表を見ながら決めるものなので、そのほうが迷わない
- 開始したあとは配信台を組み替えさせない。選手に「配信台」と伝わったあとで
  動かすと混乱するため
- **配信台は開始の条件ではない**。配信を伴わない大会や、序盤だけ配信しない大会が
  あるので、未定のままでも開始できる（011 の `rounds_stream_before_start` 制約は
  020 で外した。決める配信台が無い大会では回戦を開始できず、選手がゲームカウントを
  入力できないままになっていた）
- 開始は取り消せる。取り消すと未確定の試合の入力欄が閉じる
- **開始前でもチャットは使える**。待ち合わせの連絡は先にしておけたほうがよい

合図は**選手が見ている場所**に出す。開始はラウンドの見出しで押されるが、選手はそこを
見ていない ── 対戦の画面を開いて相手と待ち合わせているか、対戦表を眺めている。

| 出す場所 | 開始前 | 開始後 |
|---|---|---|
| 対戦チャットの上部（`#match-chat-start`、タブの外） | 「開始待ち」灰色の帯 | 「試合開始」アクセント色の帯 |
| 対戦チャットのログの中（`.chat-start-divider`） | — | 「試合開始 20:15」の区切り線 |
| 画面下端の「あなたの対戦」（`.own-match-status`） | 「運営の開始待ち」 | 「試合開始」の札 |
| 対戦表のカード（`.result-status`、当事者だけ） | 「運営の開始待ち」 | 「試合開始 — 開いて対戦」 |

チャットの帯だけは、**開いている最中に始まったときに一度だけ光らせる**（`.is-new`）。
静かに書き換わると、下を向いている数秒のあいだに見逃す。開いた時点で既に始まっていた
場合は光らせない ── 毎回光ると印としての意味が無くなる。ログの区切り線は、あとから
読み返したときに「どこまでが待ち合わせの相談か」を示すためのもので、開始時刻
（`tournament_rounds.started_at`）と発言の時刻を突き合わせて位置を決めている。

配信台を一度も決めていない回戦には `tournament_rounds` の行が無いので、開始は
UPDATEではなく**UPSERT**で行う（UPDATEだと0行で「成功」してしまい、運営だけが
開始したつもりになる）。入力の側では `round_is_started` を確認するので、
画面の出し分けを抜けても開始前の入力はDBで弾かれる。

回戦は**ブラケットの `rounds` 配列の位置（0始まり）**で持つ。ラウンド名（R1/QF/SF/F）は
表の大きさで変わる（8人大会のR1は16人大会ではR2相当）ので、位置のほうが崩れない。

### 選手によるゲームカウントの入力

運営が全試合を入力しなくて済むよう、**選手は自分が出ている対戦のゲームカウントを
入力できる**（運営がその回戦を開始してから）。**当事者のどちらが入れても、
その場で確定して対戦表が進む**。

```
選手A または 選手B: カウントを入力 ──▶ brackets と matches に反映（即確定）
```

もとは「片方が報告 → 相手が承認」で確定する形だった。一方的な入力で勝ち上がれて
しまうのを防ぐためだったが、実際には承認する側が席を外していたり、そのまま解散
したりで、試合は終わっているのに表が進まない事態のほうが多かった。進行を止める
理由が「不正の防止」ではなく「片方が画面を見ていない」になっていたので、承認は
撤廃した（`supabase/migration-018.sql`）。

代わりに**食い違いは事後に運営が直す**。誤りに気づいた側が対戦チャットの
「運営に報告」で伝え、運営が `editMatch` で訂正する。確定後の訂正はもともと
運営にしかできないので、直せる人と直し方は変わっていない。

**入力する場所はチャットの中**（`js/matchChat.js`）。対戦表の枠は幅220pxで入力欄には
狭く、待ち合わせの会話もそこで起きているため。対戦表側には「運営の開始待ち」の
1行だけを出して、チャットへ送り出す。入口は自分の行のタップと 💬 ボタンで、
これまでと同じ。開始したあとに対戦表へ何も出さないのは、入れた瞬間に確定する以上
「入力済み・相手待ち」のような途中の状態が存在しないため。

チャットは画面（`view-*`）の外にあるダイアログなので、`routeFromHash` の描き直しでは
更新されない。相手の入力や回戦の開始に追従させるため、全件取得のたびに
`syncOpenChat()` で開いているダイアログを合わせ直す。

- **確定後の訂正は運営だけ**。次ラウンド以降へ連鎖する取り消しになるため（`editMatch`）
- **「不戦勝で確定」は運営だけ**に出す。「相手が来なかった」の判断は運営が行うこと
- 選手側の送信には確認ダイアログを1枚挟む。承認という引き返す機会が無くなったぶん、
  押す前に一度だけ数字を見せる

**選手は `brackets` に直接書けない**（`brackets_write` は運営限定）。ここを緩めると
対戦表を丸ごと書き換えられてしまうので、確定の処理は `security definer` の
`report_match_result` に閉じ込めてある。この関数は「その1試合の結果を入れて、
勝者を次の枠へ送り、`matches` に1行足す」以外のことができない。JSONの組み直しは
`apply_match_result_json` が行い、内容は `js/bracket.js` の `applyWinner` と同じ。
両者が同時に押しても二重に確定しないよう、関数の頭で `brackets` の行を
`for update` で押さえてから確定済みかどうかを見る。

そのため、対戦表の描画には2つのコールバックがある。`onChanged`（運営の勝敗入力）は
対戦表そのものをDBへ書き戻すので選手が呼ぶとRLSで弾かれる。選手の操作は
`onRefresh` を呼び、書き込みが済んだDBから取り直すだけにする。

#### 書き戻しの競合

運営は**手元の対戦表を丸ごと書き戻す**。その間に選手が結果を確定させていると
（`report_match_result` はDB側で直接反映する）、気づかずに上書きして消してしまう。
そこで `brackets.updated_at` を版数として持ち、読み込んだときの値を覚えておいて、
**書き戻す直前に突き合わせる**（`js/db.js` の `assertBracketUnchanged`）。
食い違っていれば保存を中断し、再読み込みを促す。失敗時は `persist` が
`refreshFromDb` を呼ぶので、画面はDBの正しい状態に戻る。

判定を「確定済みの試合が増えているか」にしてはいけない。運営が結果の確定を取り消す
操作（`editMatch`）でも手元だけ未確定に戻った状態になるため、正しい操作を誤検知する。
版数で見れば操作の向きに依らない。

### 対戦カードごとのチャット

進行中の大会で、対戦相手と待ち合わせや進行の相談ができる。**部屋はブラケットの試合1つに
つき1つ**で、同じ相手でもラウンドが違えば別の部屋になる。入口は対戦表の中で、
**自分がいる側の行をタップする**と開く（枠の下端のボタンからも開ける）。

- **読み書きできるのは その試合の当事者と運営だけ**。他の選手にもゲストにも見えない。
  閲覧が全員に開いている他のテーブルと違い、`match_chat_messages` は `anon` に
  権限を一切与えていない
- **2v2ではチーム同士の4人**が同じ部屋に入る
- **勝敗が確定したら読むだけ**になる。直前のやりとりを見返してスコアの行き違いを
  確かめられるよう、閲覧は残す。運営は確定後も書ける（介入のため）
- **削除できるのは運営だけ**。本人にも消させない。消えた発言を巡って
  「言った/言わない」になるより、運営が判断する形にする
- 大会を削除すると `ON DELETE CASCADE` で一緒に消える

**誰がどの部屋に入れるかは、参加者をチャット側にコピーせず、そのつどブラケットのJSONを
読んで判定する**（`can_use_match_chat`）。コピーを持つと、参加者の入れ替えや連鎖的な
結果の取り消しでブラケットだけが変わり、2つの情報がずれる。判定の根拠は常にブラケット
1つに寄せる。当事者かどうかは `tournament_entries` の `coalesce(team_id, player_id)` が
ブラケットのスロットのIDと一致するかで見るので、個人戦とチーム戦を同じ式で扱える。

更新は**Realtimeではなく、画面を開いている間だけの間欠取得**にしている（`js/matchChat.js`）。
理由は2つ。既存の購読は「どれかのテーブルが変わったら全データを取り直す」作りなので、
チャット1通ごとに全員が全件取得することになる。そして、当事者にしか見せないデータを
ブロードキャストに載せると、購読側のRLS適用の設定ミスがそのまま漏洩になる。
SELECTで取りに行けば、必ずポリシーを通る。

### 運営への報告

チャットでもめたとき、当事者が**一言添えて運営へ報告**できる（チャットの「運営に報告」）。
未対応の報告がある大会は、**運営の画面でだけ**次の3か所に印が出る。

1. 大会一覧（募集中・履歴）のカードに「⚠ 未対応の報告 N件」
2. 大会詳細の「大会情報」の先頭に帯
3. 対戦表で、報告のあった試合の枠が赤くなる

報告からチャットまで一直線でたどれるようにするためで、報告した本人にはチャットの中に
「報告済み」の控えだけが出る（相手には見えない）。運営が「対応済みにする」を押すと
印が消え、誰がいつ閉じたかが `resolved_by` / `resolved_at` に残る。

- **報告できるのは その試合のチャットを使える人**（`can_use_match_chat` を再利用）
- **報告は誰にも削除させない**（`delete` のGRANTを与えていない）。消せてしまうと
  もめごとの経緯そのものが失われる。大会を消せば `cascade` で一緒に消える
- 報告の**中身は書き換えられない**。更新できる列を `resolved_at` / `resolved_by` の
  2列だけに絞ってある（RLSは行しか制御できないので、列はGRANTで絞る。
  `players.role` と同じ考え方）

報告だけは**1分間隔で取りに行く**（`js/app.js`）。全件取得の保険はRealtimeが届いている間
15分に1回で、トラブルの報告が運営に伝わるには遅すぎるため。チャットと同じ理由で
Realtimeには載せられないので、行数のごく少ないこのテーブルだけを別に見る。
未対応の顔ぶれが変わったときだけ描き直し、入力中は次の周期へ持ち越す
（描き直しは編集中のフォームを閉じてしまうため）。

### 最終順位

シングルエリミネーションでは、何回戦で負けたかで順位が決まる。決勝の敗者が2位、
準決勝で負けた2人が同率3位、準々決勝の4人が同率5位…と、1つ前のラウンドになるごとに
枠が倍になる。`js/bracket.js` の `finalStandings` が **16位まで** を算出し、
確定済みの大会ページに表示する。参加人数ではなくBYEを含めた表の大きさを基準にする。

運営が募集を使わず参加者を直接選んで大会を立てる経路も残してある（大会作成画面の
「運営が参加者を直接選ぶ」）。この場合は作成と同時に `running` になる。

### 定員の扱い

定員の判定は**データベースのトリガー**で行う。クライアント側で残枠を確認してからINSERTする方式は、
2人が同時にボタンを押したときに両方とも通ってしまうため。大会行を `FOR UPDATE` でロックしてから
数えることで、同じ大会へのエントリーを直列化している。

トリガーは**文単位のAFTER INSERT**（遷移テーブル `new_entries` を使う）。当初は行単位の
BEFORE INSERTだったが、次の2つの不具合があった。

- 締切時にシード順を `upsert` で書き戻すと、既存行の更新であってもINSERTトリガーが発火し、
  **定員ちょうどまで埋まった大会が締め切れなかった**
- 行単位トリガーから見た `count(*)` には、同じINSERT文で挿入中の行が含まれない。
  そのため**一括挿入では定員が素通り**していた

文単位なら、何行まとめて入っても挿入後の最終人数を1回だけ検査すればよい。

なお、運営が参加者を直接選ぶ大会では定員を設定しない（`capacity = null`）。定員は
エントリー募集を制御するためのもので、直接指定した参加者を自分で弾いてしまうため。

### チーム戦（2v2）のエントリー

チーム戦は「エントリー」ボタン1つでは終わらない。**申し込む人がチーム名と相方を
その場で決める**フォームを開き、送信するとチーム行とメンバー2人のエントリー行が
まとめて作られる。相方は登録済みの選手から選ぶ（そうすることで、相方の選手ページにも
出場と成績が残る）。選ぶ欄はドロップダウンではなく**名前かゲームIDで検索して選ぶ**形に
している。選手が数十人になるとドロップダウンからは探せないため。検索欄が空のうちは
候補を出さない（全員を並べても目当ての人は探せず、たまたま先頭に来た人を押し間違える
ほうが起きやすい）。同姓同名や表記ゆれで取り違えないよう、名前にゲームIDを添えて出す。

この登録だけは **RPC `enter_tournament_as_team` を通す**。RLSの `entries_insert` は
「自分の選手行だけ」しか挿入させないため、申し込んだ人が相方の行を入れられないから。
`security definer` の関数の中で募集中かどうか・重複エントリー・チーム名の重複・
定員（チーム数）を検査し、大会行を `FOR UPDATE` でロックしてから数えるので、
同時に申し込まれても定員を超えない（個人エントリーのトリガーと同じ考え方）。

取り消し（`cancel_team_entry`）は**メンバーなら誰でもできる**。2人組は片方が抜けた
時点で成立しないので、「申し込んだ人だけ」に絞ると、その人が離脱したときに相方が
チームを畳めなくなる。取り消すとチーム行が消え、メンバーのエントリー行も
`ON DELETE CASCADE` で一緒に消える。

**運営が参加者を直接選ぶ経路は、チーム戦では使えない**。あの画面は選手を並べるだけで
チーム名と組み合わせを決められないため、対戦方法に2v2を選ぶと選択肢ごと閉じる。

### 参加者の入れ替え

`js/db.js` の `replaceEntries` は「先に登録してから、不要な行を削る」順序で書く。
逆にすると、削除が済んだあとに登録が失敗したときエントリーだけが消え、
**参加者0人の大会**が残る（実際にこの不具合が起きた）。同じ理由で、大会作成時に
参加者やブラケットの登録が失敗した場合は、作りかけの大会を削除して取り消す。

## 8. ランキング方式（LumiRank軽量版）

### 背景

本家LumiRankは、互いに直接対戦しない世界中の選手を比較するため、Tier別ポイント表・地域ポイント・
反復averaging等の重い仕組みを持つ。本ケースは同一コミュニティ内で25〜60人が繰り返し対戦するため
対戦グラフが密で、重い仕組みは不要。**核（相手の強さで重み付けした反復スコアリング）だけを残す**。

### 残す要素

- 相手の強さで重み付けした勝敗スコア
- スコアが収束するまでの反復計算（密なグラフなら数回で収束）
- 大会規模による重み付け

### 省く要素

- Tier別ポイント表 / 地域ポイント / superregion（全大会が同一コミュニティ内のため不要）
- Hidden Boss値（不要）
- 出場ペナルティは「ランク付け対象は最低N大会出場」の足切りに簡略化

### averaging方式で起きた不都合（現在の式にした理由）

当初は本家に倣い、1試合ごとの観測値（勝てば「相手のスコア＋ボーナス」、負ければ
「相手のスコア−ボーナス」）の**平均**にスコアを収束させていた。これはシングルエリミの
ブラケットで破綻する。

平均を取る式では、収束したスコアが次を満たす：**自分が倒した相手のスコアは
「自分のスコア−ボーナス」に落ち着く**（その相手の唯一の試合が自分への敗戦なら、
定義からそうなる）。すると自分がその勝利から受け取る観測値は

```
（自分のスコア − ボーナス）＋ ボーナス ＝ 自分のスコア
```

で、**平均を1ミリも動かさない**。つまり勝ち上がりが score に寄与せず、スコアは
「誰に負けたか」だけで決まってしまう。

実際にTest大会（21人・20試合）で次が起きた。

| 選手 | 成績 | 最終順位 | 旧スコア |
|---|---|---|---|
| Syrup | 0勝1敗（初戦で優勝者に敗退） | 16位 | 96.974 |
| 暗黒う豆 | 2勝1敗（2回勝ち上がって優勝者に敗退） | 8位 | 96.974 |

小数第3位まで一致し、画面表示（`toFixed(1)`）では完全に同じ 97.0 になった。さらに
0勝1敗の選手が1勝以上した選手を追い抜く並びにもなっていた（2位の選手に初戦で当たった
0勝1敗の選手が、別ブロックで2勝した選手より上）。**平均方式は「強い相手に当たったか」を
測る式であって、「勝ったか」を測る式ではない**ため、勝ち上がりを評価する指標としては
使えない。

そこで、勝敗の重みを固定ボーナスではなく**期待勝率とのズレ**で測る式に置き換えた
（下記アルゴリズム）。格上に勝てば大きく上がり、格下に勝ってもわずかしか上がらないが、
**勝てば必ずプラス・負ければ必ずマイナス**になるので、勝ち上がりが必ずスコアに残る。

### ランキングに反映する大会の条件

大会の試合は自動でランキングに乗るが、**次のすべてを満たす大会だけ**をスコア計算の対象とする
（判定は `js/rankingEligibility.js`。保存はせず、そのつど大会の内容から算出する）。

1. **参加人数が16人以上**
2. **対戦方法が 1v1 またはリレー**（`tournaments.match_type` が `1v1` / `relay`）
3. **配信元がYouTubeのURL**（`tournaments.stream_url` のホストが `youtube.com` / `youtu.be`）
4. **運営が反映を外していない**（`tournaments.ranking_opt_in` が真。既定は真）

1〜3は「数えられないから外れる」条件。少人数の大会やチーム戦（`2v2` / `other`）の勝敗まで
レートに混ぜると、個人の実力を表す指標として成り立たなくなるため。`match_type` が `null` の
大会（この仕組みより前に作られたもの）も対象外で、運営が大会情報の編集で選び直すと反映される
ようになる。

3は「誰でも後から確認できる形で行われた大会か」を見る条件。スコアの根拠になる以上、当事者
以外にも試合を追える必要がある。見るのは運営が入れた配信元URLのホスト名だけで、実際に配信
されたか・URLの先が配信なのかアーカイブなのかまでは判定しない（そこはURLを載せる運営の
責任として扱う）。この条件より前に作られた大会は配信元が空欄のことがあり、その場合は対象外
になる ── 大会情報の編集でURLを入れれば、次にランキングを作成したときから入る。

4は「数えられるが数えないと決めた」設定。エキシビションや練習会のように、条件は満たすが
順位に混ぜたくない大会のための逃げ道で、大会作成のときに運営が決め、あとから大会情報の
編集でも変えられる。**性質が違うので、画面でも別の言葉で伝える** ── 条件を満たしていない
大会には足りないものを並べるが（募集中なら人数が増えて満たされることもある）、運営が
外している大会にそれを並べても読む人の役に立たない。切り替えても公開済みのランキングは
作り直されない（あれは集計時点の写し）。次にランキングを作成したときから効く。

`2v2` については二重に守られている。仮にこの条件を外しても、チーム戦の試合は
`matches` の選手列が空なのでスコア計算に入れようがない（前章「チーム戦の試合の記録」）。

除外するのは**スコアだけ**で、ランキングカードの「好成績」（優勝・ベストN）は対象外の
大会からも選ぶ。優勝は優勝として讃えたいため。2v2の優勝もここに含まれる
（`js/ranking.js` の `countTournamentsByPlayer` がチーム戦の試合をメンバー全員の
出場として数えている）。足切り（最低出場大会数）に数えるのはスコアの根拠と揃えて
反映対象の大会のみ。

反映されるかどうかは大会詳細ページの「大会情報」の先頭に印として表示し、条件を満たさない
場合は足りない条件もそのまま出す。

### アルゴリズム（期待勝率型・実装は `js/ranking.js`）

やっていることは「各選手にスコアを1つ与え、そのスコア差から出る期待勝率で実際の勝敗が
いちばん起こりやすくなる組み合わせを探す」＝ Elo／Bradley-Terry の最尤推定。

1. 各選手のスコア S を全員同じ初期値（1000）で開始
2. 期待勝率は `P(A勝ち) = 1 / (1 + 10^((S_B − S_A) / 400))`（400点差で約91%）
3. 1試合ごとに **勝ち星の余剰 =（勝ち1／負け0）− 期待勝率** を両者に足す（勝者にプラス、敗者に同じ値のマイナス）。この余剰に**大会規模の重み**（平均を1とした相対値）を掛ける
4. さらに全選手へ「初期値と同じ強さの仮想相手と2回引き分けた」ぶんを足す（下記）
5. 選手ごとに余剰の合計と「そのスコア帯での効きの大きさ」から動かす量を決め、全選手を同時に更新（対角ニュートン法）
6. 動きが 0.01 点未満になったら収束（実データでは十数回）
7. 最後に #1 が 100 になるようスケーリング
8. 最低出場数に満たない選手はランク付け対象外

**仮想の引き分け（priorMatches）を入れる理由**：この式は無敗の選手のスコアを無限に
上げられてしまう（優勝者、および1試合だけ勝って終わった選手）。初期値へ引き戻す力を
全員に同じ形で足すことで、試合数の少ない選手のスコアは初期値の近くに留まり、試合を
重ねた選手ほど成績どおりの位置まで動ける。実データでの効き方：

- 優勝者に1勝してすぐ負けた選手（2試合）→ 7位。1勝しただけの選手が上位を占めない
- 下位の選手に3連勝して終わった選手（3勝0敗）→ 3位。無敗は評価されるが1位にはならない

**大会ごとの寄与（発表画面の「好成績」）**：`scoreContributionsByPlayer` が返す `impact` は
その大会で挙げた勝ち星の余剰の合計。プラスならスコアを押し上げた大会。順位（優勝・ベスト4）
とは一致しないことがあり、少人数の大会で優勝するより強豪ぞろいの大会で上位に食い込む
ほうが上に来る。

### 確定パラメータ

- **スコアの物差し**：400点差で期待勝率91%（Eloと同じ）
- **仮想の引き分け**：2試合ぶん
- **スケーリング上限**：#1 = 100
- **足切り大会数 N**：1（1大会以上の出場でランク付け対象）
- **ブラケットのシード配置**：現在のランキング順を元にシードする（上位が早期に当たらないよう配置）

同点のときの並びは **勝ち数 → 名前** で決める。対称なブラケットの別ブロックでまったく同じ
形の成績になると小数点までスコアが一致しうるため、試合データの読み込み順で並びが
変わらないようにしてある。

## 9. 大会規模Tier（表示用ラベル）

コミュニティの慣習に合わせ、出場枠の数から `js/tournamentTier.js` が自動でTierを判定する
（保存はせず、都度算出）。チーム戦では16チームの大会が「Tier 2」になる（32人ではない）。
表の大きさ＝勝ち上がりの重みと釣り合わせるため。
10人刻みで Tier 1（1〜9人）〜 Tier 6（50〜59人）、**60人以上は「大規模」**判定。
ランキング計算の `weight` とは無関係の独立した区分で、大会情報・大会履歴一覧に表示する。

## 10. トーナメント形式の実装順

1. **シングルエリミネーション** ← 実装済み
2. **ダブルエリミネーション**：敗者ブラケットを追加
3. **総当たり（リーグ）**：全組み合わせ生成

`tournaments.format` に `double_elim` / `round_robin` を入れられるようスキーマ側は用意してある。
